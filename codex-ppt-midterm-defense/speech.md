## Slide 2: 复杂长程任务的协作问题

复杂长程任务通常不只是一次问答，它会包含任务拆解、角色协作、证据整理、执行检查和结果合成等步骤。对于这类任务，只看最终答案很难判断中间过程是否可靠，也很难定位错误来自哪一步。

这页把问题拆成三个方面：任务链路比较长，多个 Agent 之间需要传递中间结论，过程验证需要有结构化依据。我的课题从这个问题出发，把协作过程本身作为研究对象，关注每一步是否可记录、可检查和可复用。

## Slide 3: 本课题的研究目标

本课题的目标是构建一个可验证的多 Agent 协同框架。具体来说，第一是设计结构化的 Agent 间通信格式；第二是根据任务画像选择协作拓扑；第三是记录完整的运行轨迹；第四是用合约验证机制评估协作过程。

这四个目标分别对应后续系统里的 Contract、Router、Trace 和 Verifier。它们共同支撑一个基本闭环：任务进入系统后，系统能够决定如何协作，记录协作过程，并给出过程级验证结果。

## Slide 4: 系统总体架构

系统整体流程从用户任务开始。任务首先进入 Task Profiler，生成任务画像；Router 根据画像选择执行结构；随后由 Orchestrator 或 GraphExecutor 组织 Agent 执行；执行过程中，每一步输出都被包装成 ContractMessage；Verifier 对这些合约消息进行检查；最后 Trace 和 Memory 保存运行记录。

这条链路对应 README 中的架构设计，也对应当前代码中的核心模块。它的作用是把多 Agent 协作从一组松散调用，整理成一条可以观察、可以验证、可以测试的执行路径。

## Slide 5: 合约消息机制

合约消息是这个框架的基础数据结构。每个 Agent 的输出不直接作为自由文本传给下一个角色，而是被组织成 ContractMessage。里面包含角色、子任务、主张、证据、动作和不确定性等字段。

这种结构让验证器可以检查每一步是否有明确主张，主张是否有证据支撑，动作是否完整。后面的 contract report、json trace 和协议记忆都依赖这层结构化记录。

## Slide 6: 任务画像与基础拓扑路由

任务画像用四个维度描述任务特征：是否需要工具、任务不确定性、步骤数量和风险水平。基础路由器会根据这些特征在三种拓扑之间选择执行方式。

简单任务走 SINGLE_AGENT，主要是 Executor 和 Verifier；中等复杂任务走 SUPERVISOR_WORKER，加入 Planner 先做规划；高风险或需要更强检查的任务走 REVIEW_LOOP，增加执行和验证的迭代。这个基础路由为后续定量路由提供了对照基线。

## Slide 7: 编排器执行流程

Orchestrator 是默认路径的主控模块。它先完成任务画像和拓扑选择，然后检索协议记忆，按拓扑顺序执行 Agent 链，再对合约消息进行验证。如果验证失败并且预算允许，系统会进入 REVIEW_LOOP 做更强检查，最后由 Synthesizer 生成最终答案。

这里的 Budget 用来限制协作步数，避免模型接入后出现无意义循环。Memory 用来记录通过的协作模式，后续相似任务可以获得提示。这个流程把路由、执行、验证和存储串成了一个完整控制链。

## Slide 8: 定量 Router 设计

定量 Router 是当前阶段的重点扩展。它不只返回一个基础拓扑名称，还会生成 TopologySpec。TCI 在这里表示任务复杂度指标，它和任务跨度、依赖深度、工具负担、证据负担、不确定性和风险等因素相关。

TopologySpec 中包含 task_type、capability_needs、节点和边的预算，以及 blocked 状态。CapabilityNeeds 会描述任务需要哪些协作能力，例如 planning、verification 和 synthesis。对于要求“根据给定材料”但没有提供材料的任务，系统会标记 blocked 并返回原因。

## Slide 9: 协作图生成与执行

在 Quant 路径中，TopologySpec 会进一步转成 CollaborationGraph，然后由 GraphExecutor 执行。图生成器根据 capability_needs 选择节点，例如 Planner、Executor、Verifier 和 Synthesizer，并生成受约束的顺序 DAG。

GraphExecutor 会记录 executed_nodes、skipped_nodes、review_loops_used 和 execution_mode 等元数据。当前版本先支持顺序 DAG 和受预算约束的 review loop，这样可以保持实现可控，也方便测试验证。

## Slide 10: CLI 运行报告

为了让运行过程可观察，CLI 提供了几类输出方式。contract report 用于展示任务画像、拓扑选择和合约验证摘要；json trace 用于输出完整结构化轨迹；save-run 会把运行记录保存到文件；show-topology 用于展示生成的协作图。

这些输出对后续实验很重要。因为我们需要比较不同协作路径的表现，就必须能稳定记录每次运行的画像、拓扑、消息、验证结果和最终答案。
